# 技巧与成本：把 45 分钟视频压成 3 万字输入稿

记录这条流水线为什么长这样，以及哪些坑已经踩过。

## 1. 字幕：不要用检测，直接识别

硬字幕的特征非常稳定：**白色填充 + 黑色描边 + 单行 + 居中 + 字高约 55—70px（1080p）**。

做法：

```python
band = frame[int(h*0.70):, :]                       # 只看底部 30%
mask = (np.max(band, axis=2) < 55)                  # 近黑像素 = 描边
d = cv2.dilate(mask, np.ones((2,15), np.uint8))     # 横向连字成行
# 连通域里筛：高度 38—110px、宽度 ≥120px，取最宽的一条
crop = band[y-6:y+h+6, x-6:x+w+6]
engine(crop, use_det=False, use_cls=False)          # rec-only
```

实测：

| 方案 | 单帧耗时 | 识别质量 |
|---|---|---|
| 整带 det+rec（1080p） | 1.0—2.5 s | 好，但会把画布小字一起识别 |
| 整带缩放 0.6 后 det+rec | 1.5 s | 无提升 |
| **描边定位 + rec-only** | **0.03—0.08 s** | 与 det+rec 相同 |

结论：**字幕用几何定位，画布才用检测**。仅这一项就让 45 分钟视频的字幕提取从 2 小时降到 8 分钟。

## 2. 画布：控制调用次数，而不是控制单次耗时

画布整帧 det+rec 的成本随**检测框数量**线性增长：

| 画面 | 框数 | 耗时（6—8 线程） |
|---|---|---|
| 稀疏页（十几行） | 15—20 | 3—4 s |
| 密集文档页 | 60—90 | 8—14 s |
| 满屏图表（片头） | 170+ | 14—40 s |

所以优化方向不是"让单帧更快"，而是"少跑几帧"：

- 每 1 秒算一次画面差异（缩到 320×180 灰度）；
- 差异 > 2.5 且距上次 ≥15 秒才识别；
- 最长 30 秒强制识别一次。

45 分钟视频最终只跑 **90—110 次**画布 OCR，约 6—9 分钟。

## 3. 解码：seek 是最大的隐形开销

第一版用 `cap.set(CAP_PROP_POS_MSEC, t)` 逐秒定位，看起来只取 2700 帧，实际上每次 seek 都要重新找关键帧 + 解码，单次 50—150 ms，累计十几分钟，而且 CPU 占用很低（在等 I/O）。

改成顺序 `cap.grab()` 跳帧、需要时 `cap.read()`：

```python
if i % 15 == 0:                 # 字幕 2fps
    ok, frame = cap.read()
elif i % 30 == 0:               # 画布 1fps
    ok, frame = cap.read()
else:
    ok = cap.grab()             # 只解码不转 BGR，便宜
```

45 分钟视频的纯解码约 2—4 分钟，与 OCR 并行后不再是瓶颈。

## 4. 并行：两条 6 线程，不要四条 4 线程

- 4 进程 × 4 线程：争抢严重，密集帧单帧从 14 s 涨到 40—90 s，整体反而更慢。
- **2 进程 × 6—8 线程**：接近线性，16 核机器上 45 分钟视频约 20—25 分钟。
- 进程按**时间中点**切两半，各自从关键帧起播即可，不需要精确对齐。

## 5. 失败的尝试

| 尝试 | 结果 |
|---|---|
| Windows.Media.Ocr（系统 OCR） | 速度极快（0.07 s/帧），但中文准确率差，会把"单位缴纳"识别成"单 亻 立 纳"，不可用 |
| 按行切分 + rec-only 做画布 | 快 3 倍，但会把句子切成碎片、顺序错乱，质量不可接受 |
| 缩小到 720p/540p 再做 det+rec | 只快 20%—30%，因为瓶颈是逐框识别，不是检测 |
| `--download-sections` 分段下载 + `--force-keyframes-at-cuts` | 会触发重编码，60 秒片段卡住数分钟，已弃用 |
| 用复制 Edge 配置的方式取 Cookie | Edge 的 v20 应用绑定加密与配置路径绑定，换路径后登录态失效，只得到匿名 Cookie |

## 6. 成本模型

一次"探索式"完成的真实开销：178 个模型步、约 1800 万输入 token（其中 89% 命中缓存）、10.7 万输出 token，折算约 ¥20。

流水线化之后：

- 输入 = `摘要输入.md`（3.2 万字 ≈ 2 万 token）+ 模板，**只读一次**；
- 输出 = 一篇 1.5—2.5 万字总结 ≈ 1.4 万 token；
- 合计约 **3.4 万 token**，按同一单价约 **¥0.1—0.3**。

差额来自两件事：**不再试错**、**不再把长日志反复读进上下文**。后者尤其关键：一份 7 万字的 `口播全文.txt` 每读一次就是 5 万 token，读三遍就抵得上一整条流水线。

## 7. 给多视频批处理的建议

1. 先用 `批量处理.ps1` 把 N 条视频的 `摘要输入.md` 全部生成好（纯 CPU，可挂着跑）；
2. 每条视频**单独开一个会话/子代理**写总结，互不污染上下文；
3. 总结只读 `摘要输入.md`，写完即止，不回头核对原始 OCR；
4. 需要核对数字时，只 grep `口播全文.txt` 的对应时间段，不要整篇读入。

## 8. 已知误差

- 形近字：并/井、补/盈、缴/至、博/搏——总结阶段按语义校正，并在文末列出"待核"；
- 数字：中文数字与阿拉伯数字混排时可能丢位（如"2.238 元"实为"2238 元"），重要数字建议回看画布 OCR 的原文；
- 时间戳是采样时间，不是字幕精确起止。
